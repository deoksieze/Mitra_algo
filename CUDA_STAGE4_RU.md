# Этап 4: pairing на GPU без таблицы всех сочетаний

Метод `CudaBackend::pairing` теперь вычисляет пары на GPU. Сохраняются условия CPU-reference, состав пар и порядок `(позиция источника в selected, позиция цели в selected)`. Индекс кривизн, count → prefix sum → fill и сортировки работают на device. Код CPU pairing не изменён.

На GPU теперь выполняются фильтрация выбранных точек, pairing и построение голосов. Подготовка геометрии, кривизны, случайная выборка, mean shift и проверка участков остаются CPU. Следующий этап — GPU mean shift.

## Условия CPU-reference

Для двух позиций `a < b` выбранной последовательности берутся mesh IDs `i=selected[a]`, `j=selected[b]`:

```text
M = max(abs(kmin[i]), abs(kmax[i]), abs(kmin[j]), abs(kmax[j]), 1e-10)
tolerance = pair_threshold * M

abs(kmin[i]-kmin[j]) <= tolerance
abs(kmax[i]-kmax[j]) <= tolerance
distance(vertex[i], vertex[j]) >= 0.03 * box_size
```

Пары не подвыбираются случайно. Все позиции selected участвуют, как в нынешнем CPU-reference. Прежние эвристики исторического MATLAB/C++ pairing не возвращались. Неравенства, double precision, sqrt в проверке расстояния и порядок арифметики сохранены. Проверка valid происходит раньше, в pruning; pairing сам её не добавляет.

## Как работает индекс кандидатов

1. На host упаковываются только выбранные координаты и две кривизны: пять SoA-компонент. Host проверяет конечность значений и диапазон selected IDs.
2. GPU создаёт ordinal `0..S-1` для каждой позиции selected и сортирует пары `(kmin, ordinal)` через `cub::DeviceRadixSort::SortPairs`.
3. Поток на источник бинарным поиском находит необходимый диапазон kmin целей. Это предварительный фильтр: он может включать лишние кандидаты, а окончательный predicate точно повторяет CPU.
4. Блок на источник параллельно проверяет кандидатов и суммирует число принятых целей через `cub::BlockReduce`. Цели с ordinal <= source ordinal исключаются.
5. `cub::DeviceScan::ExclusiveSum` строит 64-битные смещения. Итог сравнивается с max_pairs и INT32_MAX **до выделения массивов выхода**. Превышение — явная ошибка, без усечения.
6. Блок на источник повторяет проверки пакетами по **256 кандидатов**. `cub::BlockScan` назначает позицию принятой цели в диапазоне источника.
7. `cub::DeviceSegmentedRadixSort::SortKeys` сортирует принятые target ordinals отдельно для каждого источника. Последний kernel переводит ordinals обратно в mesh IDs и заполняет Pairs.a/b.

Последняя сортировка нужна потому, что порядок kmin отличается от входного порядка selected. Сортировка mesh IDs здесь была бы ошибкой: интерфейс принимает и переставленную последовательность. Равные ключи, повторные IDs и пустые сегменты сохраняют CPU-семантику. Атомики не определяют порядок результата.

### Почему диапазон не теряет допустимые пары

Пусть `Mi=max(abs(kmin[i]),abs(kmax[i]),1e-10)`, аналогично Mj; t — относительный допуск. В точной арифметике для допустимой пары обе координаты кривизны удовлетворяют `abs(ki-kj)<=t*max(Mi,Mj)`. Если Mj>Mi, то `Mj<=Mi+t*Mj`, значит `Mj<=Mi/(1-t)`. Отсюда необходимая граница по kmin:

```text
kmin[j] находится в [kmin[i]-t*Mi/(1-t), kmin[i]+t*Mi/(1-t)]
```

CPU округляет и разности, и произведение допуска. Поэтому в индексе используется увеличенный `t_safe=t+8*epsilon`, где epsilon=2^-52. Для t_safe<1 граница вычисляется по t_safe, расширяется дополнительным padding и nextafter наружу. При t_safe>=1 берётся полный диапазон. В окончательном predicate остаётся исходный t.

Расширять только готовые endpoints на один ULP недостаточно при t почти равном 1: округлённый CPU predicate может принять пару за пределами границы, выведенной в точной арифметике. Для такого случая добавлен отдельный regression fixture. При overflow радиуса интервал становится полным, сохраняя корректность.

## Память и сложность

S — число выбранных точек, P — число принятых пар. Не выделяются массив flags для всех S² сочетаний или таблица всех кандидатов.

Постоянные device buffers этой реализации до выхода:

- source SoA: 40*S байт; отсортированные ключи: 8*S;
- source ordinals, sorted ordinals и selected IDs: 12*S;
- два диапазона на источник: 16*S;
- counts и offsets: 16*(S+1).

Итого **92*S+16 байт**. После проверки бюджета добавляются accepted ordinals, ordered ordinals и две компоненты выхода: **16*P байт**. Дополнительно CUB выделяет запрошенный им временный storage для конкретной операции; временные allocations sorting/scan освобождаются между операциями. CUB scratch имеет линейный размер по входу соответствующего примитива. Host держит упаковку 40*S и конечный результат 8*P байт; входные владельцы остаются у вызывающего кода.

Счётчики/смещения 64-битные, IDs 32-битные. S ограничен INT32_MAX; при таком S сумма числа пар помещается в uint64_t. P ограничивается бюджетом и диапазоном IDs. Candidate packet в fill имеет максимум 256 элементов, shared memory CUB фиксирована размером блока.

Индекс уменьшает число проверок для разнесённых кривизн. Если кривизны одинаковы или допуск широк, диапазоны могут содержать все S точек: вычислительная работа остаётся O(S²). Сами допустимые пары тоже могут быть квадратичны — их материализацию ограничивает max_pairs. Линейная рабочая память не означает гарантированного субквадратичного времени.

## Код и проверки

- `src/cuda/backend.cu`: candidate_ranges, accepts_pair, count_pairs, fill_pairs, materialize_pairs и host-обвязка cuda_pairing; общие RAII и device math остаются от этапа 3.
- `tests/cuda_pairing.cpp`: прямое сравнение CPU/GPU и проверки пределов.
- `benchmarks/pairing.cpp`: измерение только pairing с одинаковыми host-входами и проверкой результата.
- `CMakeLists.txt`: новые targets symmetry_cuda_pairing_test и symmetry_pairing_benchmark.

На GPU проходят **7 групп CTest**: geometry, storage_backend, pipeline, cuda_backend, cuda_pairing, compare_cuda, pipeline_cuda. CPU-only сборка проходит прежние 3 группы. Все 7 групп также прошли в чистой Release-сборке в отдельном каталоге `/tmp/symmetry-stage4-clean`.

Pairing-тест покрывает пустую/одиночную выборку, 513 точек с полностью плотным совпадением, смешанные кривизны 777 точек, переставленные и повторные ID, равные ключи, +0/-0, малые и большие кривизны, строгие границы расстояния/допуска, t почти 1 и t=1. Проверяется совпадение **обоих массивов Pairs побайтно**, повторяемость и бюджет ровно по размеру выхода/ниже выхода. Некорректные индексы, нечисловые кривизны, context и threshold отвергаются.

На **65 536 точках** с раздельными диапазонами GPU вернул ноль пар примерно за 4.4 мс в одном измерении. Таблица всех двухиндексных сочетаний верхнего треугольника заняла бы почти 16 GiB; рабочие явные buffers здесь около 5.75 MiB плюс CUB scratch. Этот случай проверяет результат с известным ответом; CPU brute force для всех этих точек не запускался.

Сквозное сравнение reflection, rigid, partial, single при sample-ratio=1 и 0.5: features/pairs/mesh совпадают побайтно, голоса и JSON без timings совпали с нулевой численной разницей в проверенном окружении. CPU-режим также точно совпал с сохранённым бинарником этапа 3:

```bash
python3 tests/compare_cuda.py build-cuda/symmetry_cpu_cli
python3 tests/compare_reference.py \
  /tmp/symmetry-stage4-baseline/symmetry_cpu_cli build-cuda/symmetry_cpu_cli
```

Compute Sanitizer memcheck повторно запускался на новом pairing-тесте, но не смог подключить инструментирование: `Failed to initialize WDDM debugger interface`, `Device not supported`. Тест самостоятельно завершился успешно; **проверка GPU-памяти sanitizer не выполнена** из-за ограничения окружения, как на этапе 3.

## Измерения

```bash
./build-cuda/symmetry_pairing_benchmark
```

Внутри одного процесса, один прогрев каждого backend, затем три повтора; медиана host wall clock включает упаковку, allocations, sorting, kernels и H2D/D2H внутри метода. Создание backend и проверка совпадения массивов выполняются вне замера.

Синтетический вход: 10 000 выбранных точек, 100 чередующихся групп кривизн, pair_threshold=1e-6, 495 000 допустимых пар. Все повторы дополнительно проверяются на точное совпадение массивов.

| Pairing | Медиана, ms |
|---|---:|
| CPU | 81.29 |
| CUDA | 9.22 |

Получено около **8.8×** для pairing на этом наборе. Это не измерение всего конвейера и не обещание такого ускорения на произвольной сетке.

На маленькой reflection.off (132 точки, параметры benchmark по умолчанию, sample-ratio=1) pairing всё ещё дороже на GPU: около 1.49 мс против 0.09 мс CPU. CPU mean shift занимает около 950–970 мс и остаётся главным ограничением; случайный разброс его времени не означает ускорения этой стадии. Удержание данных между GPU-стадиями и kernel-level профилирование пока не добавлялись.
